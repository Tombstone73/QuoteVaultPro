# Assistant application operations

The signed-in user's request starts an investigation. Reads, calculations, record resolution, and proposal preparation do not require GO. A change does: the assistant presents the exact server-generated plan, the user confirms that plan with GO, and the execution service rechecks the actor, tenant, command arguments, record fingerprint, and confirmation token before calling a canonical service. A changed proposal needs a new GO. A replay returns the persisted result rather than executing a second write.

## Discover and prepare

`application.capabilities` lists the permission-filtered read and semantic tools available in the current session. `application.operations` describes the currently connected change adapters and their business argument schemas. It also identifies known staff-application operations whose assistant adapter is missing when the actor has the corresponding grant. An absent entry is not evidence that the underlying application lacks the operation. `application.prepare_change` invokes a connected adapter to **prepare** a proposal. It cannot execute a write. These interfaces are bounded tool calls; they do not expose SQL, source editing, shell commands, or arbitrary HTTP. File contents and model text cannot add an operation or grant permission.

The shared preparation adapters include existing Product edit, Material action, fulfillment pickup, purchase-order attachment intake, and new draft Quote creation. `quotes.inspect_configuration` reads tenant-scoped Customer contacts and active Product PBV2 choices. `quotes.prepare_create` accepts the staff Quote model's customer/contact, label or PO reference, dates, notes, shipping, discount, and line configurations. It resolves current tenant records, calculates Product prices and tax, saves only a proposal, and hands the existing `quotes.create_draft` command to GO. The Quote table has no dedicated PO-reference column; this adapter stores the reference in the Quote label and displays that mapping. The canonical Quote create service now saves parent, lines, and audit in one PostgreSQL transaction; the assistant locks its intake session and marks the saved Quote in that same transaction. A replay returns the saved Quote. The assistant reads the Quote back and checks line count and total before reporting success.

The Product edit contract has a reusable `configure_product_option_rates` operation whose rate table is keyed by the Product's actual selection values; 4 mm and 10 mm are option data, not separate assistant tools or quantity tiers. The shared rate-table validator accepts any existing option axis and requires every choice. Quantity tiers remain a separate dimension within a choice. For now its connected execution context is `unprinted_substrate` on a Coroplast Product: the existing Product-specific helper supplies print/production behavior and the UI's blank pricing editor uses that same configuration. The general PBV2 Product editor and pricing matrix already support other pricing configurations; exposing those through this assistant operation is an adapter gap, not proof that the application lacks the capability. A new substrate mode absent from the Product model or editor would be an application capability gap.

The older specialized semantic tool names remain callable during migration, but new provider guidance uses discovery and the shared preparation interface. The former `configure_blank_coroplast` Product edit operation is rejected by the current contract, so a superseded pricing proposal cannot execute with the old arguments. A provider can continue an investigation after validation feedback. The server, rather than the provider, binds the resulting proposal to a GO token.

Product publish and blank-pricing warnings are shown in the reviewed plan. Model-facing schemas do not contain warning-acknowledgement switches. GO on that exact plan is the acknowledgement; the canonical save receives it only in the GO execution path. Existing warnings are retained, and a changed warning set changes the proposal fingerprint or fails revalidation.

## Current coverage and gaps

The generated [canonical capability registry](ai-operator-canonical-capability-registry.md) enumerates existing reads and reviewed commands across customers/contacts, products/pricing, Quotes, Orders, production, fulfillment, Invoices, payments, Materials, and reporting. Its `eligible` count describes registered reads and commands, **not** complete UI parity or a guarantee that every operation can be prepared through `application.prepare_change` yet. The shared preparation bridge now connects the five adapters above. Other supported commands still have their established proposal paths. Quote creation is connected; existing Quote line editing is still limited to the separate due-date adapter, so staff editor parity is not established.

Art and file-record mutations, organization settings and role administration, Product deletion, and some advanced Product pricing controls lack canonical assistant adapters. These are integration gaps where the application has a staff operation. The registry's platform-level SQL, infrastructure, source-code, and cross-tenant entries are excluded because they are outside signed-in application authority. An assistant response must say which kind of gap it encountered; it must not present an unconnected UI operation as an inherent application limitation.

## Verification boundary

Unit and mocked service tests can verify schema discovery, permission-filtered exposure, multi-step behavior, plan binding, replay protection, and pricing examples. Transaction behavior requires disposable records in a configured PostgreSQL test database. A real provider/browser run and a DEV readback are separate evidence. A displayed diagnostic lookup reference now requires a confirmed sanitized diagnostic insert; a turn correlation ID alone never proves persistence. Neither a model statement nor a successful proposal proves a record was saved.
