# Order readiness: native resolution operations

This map identifies the existing PrintersHero operations behind the Milestone 2 read. The readiness capability does not invoke them. A role that can open a workspace is not necessarily authorized to perform every action there.

## What the Order detail actually reports

`buildOrderReadinessLights` in `shared/orderReadinessLights.ts` is presentation only; `client/src/components/orders/OrderOperationalSummary.tsx` renders it in Order detail:

- Exclude line `status` values `canceled`, `cancelled`, `void`, `voided` after trimming/lowercasing.
- `productionRequiredCount`: active lines with current `product.requiresProductionJob === true`, excluding `workflowIntent === service_fee`. This is not unfinished-production quantity.
- `actionNeededCount`: effective `workflowState || status || "new"` in `new`, `needs_design`, `ready_for_prepress`, `ready_for_production`, `on_hold`.
- `inProgressCount`: effective `workflowState || status || ""` in `in_design`, `in_prepress`, `in_production`.
- Proof badge/target use the native server proof summary, with issue/needed/draft/awaiting/approved/no-required precedence (`shared/orderProofStatus.ts:160-205`). Do not recreate proof authority from the badge.

Zero actions means **No immediate action needed**, not ready to produce/ship, and does not rule out pending customer approval. Missing proof fields currently display the UI fallback **No Proof Needed**; that fallback does not establish that proof truth loaded. The summary has no per-line blocking reasons, artwork-wait count, hold reason, production progress, physical-ready pool, or universal eligibility boolean. Investigate the corresponding native detail rather than inventing those fields.

Native `GET /api/orders/:id` uses authentication + tenant context and calls `recomputeOrderBillingStatus` before reading (`server/routes/orders.routes.ts:2143-2151`): it is not a side-effect-free endpoint. Reuse authorized native data/presentation, without silently adding that write to a purported pure adapter read.

## Concrete permission and proof-link checks for an adapter

1. Preserve server-established actor ID, tenant scope and grants. Native design/proof/prepress/production routes use `isAuthenticated` + `tenantContext`, then `assertInternalUser`: reject `isPortalCustomerIdentity(req.user)` with `PORTAL_CUSTOMER_INTERNAL_ACCESS_DENIED` (`server/routes.ts:444-477`). This is not a native domain grant named `proofing.read`. Do not treat a URL, model argument, global role or UI availability flag as authorization; a direct-service adapter must preserve route protections as well as its own registered grants.
2. `requireOrgAdmin` is an alias of `requireOrgAdminOrOwner`: checks `hasAdminOrOwnerOperationalRole(String(req.actorOrgRole ?? req.orgRole ?? ""))`, i.e. tenant **owner/admin**, not global `users.isAdmin` (`server/routes.ts:112-133`). Proof manual override and mark-proof-not-required routes use this guard plus internal/actor/tenant checks. Manual override inputs: optional exact `proofVersionId`, nonempty `overrideReason`, optional `internalNote`; mark-not-required takes a reason. Neither operation is a customer decision.
3. Early release has its own native confirmation: strict body `confirmed:true`, reason (1-2000 trimmed chars), UUID `operationId`, `proofVersionId`, 64-char `artworkFingerprint`, ISO `expectedUpdatedAt`, `expectedOwnerJobId`. `releaseProofToProductionEarly` re-queries `userOrganizations` for the actor+tenant and requires owner/admin; locks workflow and rejects changed revision/owner/state, unfinished Design/Prepress, unsuitable artwork, combined runs and fulfilled work (`proofingService.ts:4503-4564`). It leaves customer approval pending. Keep existing reason fields and required justification; `AI Override` must never erase the user's explanation.
4. For the native summary link require nonempty server `proofLineItemId` AND `canOpenProofingFromOrderStatus(proofStatus)`: only `proof_needed`, `draft_not_sent`, `awaiting_customer_approval`, `proof_issue`. Use the builder/URLSearchParams, default `slice=all`; no `orderId` or `proofVersionId` in that workspace link. A missing line returns a native missing-item message, not evidence of approval. Customer token links (`/portal/proof/<token>`) are a different capability and must not be fabricated or substituted.
5. Fulfillment detail currently uses auth+tenant and passes persisted tenant role to its service. Native `permissions.canConfirmPhysicalReadiness` uses `canEditFulfillmentHistoryNotes(role)` -> `resolveOrganizationRoleAuthority(role).grants.includes("assistant.fulfillment.add_note")`: owner/admin/manager/employee, not member/unknown. `adjustReadyQuantities` rechecks that helper plus actor. `canCompleteProductionOverride` uses owner/admin; ordinary `completeProductionFromFulfillment` checks the operator helper and its own current job/quantity/route gates. Do not collapse these distinct permissions (`fulfillment/service.ts:447-462,514-534`; `shared/fulfillmentHistoryNote.ts:10-12`; `shared/organizationRoleAuthority.ts:55-74`; `fulfillment/productionCompletion.ts:35-119`).

## Missing reasons, counts and recovery limits

- An `on_hold`/`new` count is not an artwork diagnosis. Use authorized native detail/history and report a missing reason explicitly. No aggregate-to-line allocation, automatic “resolve all”, or new business policy follows from these counts.
- Existing attention reporting explicitly marks `waiting_artwork` **count:null, available:false**: no single canonical migrated field. Proof queue count can be available while matching production-job identities are unavailable; unavailable/unresolvable is not zero. Prepress/proof/fulfillment queue metrics are not interchangeable with Order summary line counts (`assistant/productionReportingTools.ts:323-327,365-401`).
- Fulfillment quantities distinguish production-complete, ready-waiting, remaining, physical handoffs and administrative reconciliation. A queued Fulfillment owner is not unfinished production; administrative closure is not physical shipment/pickup (`shared/fulfillmentReadiness.ts:19-61,83-109,182-213`). Missing quantity evidence must stay missing, not be filled from a colored badge.
- Current proof release authority comes from `resolveLineItemProofReleaseGate`, including exact current proof/artifact and artwork fingerprint, not historical approval or `approvedProofVersionId` alone. Early release of one revision cannot authorize newer artwork (`proofGateService.ts:78-109,114-128`).
- Proof send commits version/token/audit before transport. Delivery states are `pending`, `accepted`, `failed`, `unknown`; accepted is not customer receipt or approval. Pending/unknown attempts block blind resend; retryable failure preserves exact version. Queued mail is not delivery (`proofEmailDelivery.ts:8-51`). Prepress bridge copy is separately enqueued/fail-soft after completion; completion is not proof that a local file copy finished. Refresh native truth after uncertain outcomes; do not replay unrelated stages.
- The readiness read does not register correction commands. Artwork/file edits, Design completion, proof send/response/overrides and specialized production/fulfillment recovery still require their existing staff surfaces unless a separately verified assistant adapter is connected.
